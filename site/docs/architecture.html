Architecture

Purpose

Plan Ops Hub sits between a plan sponsor (the employer) and the recordkeeper (TRAC). It turns each business request into a set of tasks and routes them to people with the right skills. For each task it gives guidance and pre-built work product, automates what is safe to automate, and commits the final result to the recordkeeper. After go-live the recordkeeper is the system of record. The hub keeps only a working snapshot of the plan.

Lifecycle → case types

Onboarding / plan setup INSTALLATION config/playbooks/installation.json trac.installPlan, then plan becomes ACTIVE ("Installation Complete")
Ongoing maintenance MAINTENANCE_CONTACT, MAINTENANCE_FUNDS, MAINTENANCE_FEES maintenance-*.json Update on TRAC

New request types are added with a new playbook JSON file plus a CaseType value. No engine changes are needed.

Key design decisions

  1. Playbooks are deterministic and versioned. The guidance layer is advisory. Which steps happen, especially regulatory ones, comes from a versioned playbook and is recorded on the case (playbookId@version). The guidance layer, including any future LLM enricher (GuidanceEnricher), may explain, pre-fill, draft or flag, but it can't add, drop or reorder steps. This keeps every case auditable.

  2. Automation level is set per step (AUTO / REVIEW / MANUAL), not per workflow. It can be overridden per client. A failed AUTO step doesn't stall the case: it becomes an exception and is routed to a person, who can fix the data and retry, or override with a written justification. Both outcomes are audited.

  3. prepare() vs execute(). Every action can describe what it will do (the drafted email, the TRAC payload, the fee calculation) without side effects. That powers both guided actions and human review. execute() performs the side effects through configured integrations (IntegrationClient) and the EmailGateway.

  4. The recordkeeper is the source of truth after go-live.

    • A maintenance or termination case first refreshes the hub's plan snapshot from TRAC.
    • Onboarding data can be corrected in the hub only before the plan is installed. After that, changes need a maintenance case.
    • Every TRAC write carries an idempotency key (caseId:stepId), so retries after timeouts never double-post. Emails are idempotent per task in the same way.

  5. Generic core, client customization via config. config/clients/<id>.json can disable steps, change a step's mode, add client-specific steps, and swap templates (see acme-premium.json). Playbooks are validated (unknown dependencies and cycles are rejected) after overrides are applied.

  6. Learning suggests; people decide. Insights measure each step (handle time, auto-failure rate, overrides, how often drafts are edited, SLA breaches, backlog by skill) and produce suggestions, for example "drafts approved unchanged 5/5, consider AUTO" or "60% of drafts edited, fix the template". Playbooks are never changed automatically.

  7. Claude assists; it doesn't decide. On request, Claude (claude-opus-5-5, structured outputs, effort medium, server-side refusal fallback) receives the step's guidance, checklist and regulatory reference, the case data, earlier step results and the prepared work. It returns a briefing, risks, extra checks and, for email steps, a rewritten draft. The guardrails are in code, not in the prompt:

    • Required facts. The executor derives the facts a template inserts (amounts, dates, names, tickers) and blocks any outgoing email that drops one, whether the draft came from the template, from Claude or from a person. A Claude draft with a missing fact is flagged in the UI before anyone tries.
    • Recipients come from plan contacts, never from the model. A non-email step never gets a draft, even if the model returns one.
    • Sponsor-supplied data goes in delimited data blocks, and the system prompt says to treat it as data and to report embedded instructions as a risk.
    • Results are cached per task, keyed by a hash of the prompt, so unchanged tasks don't pay twice. Each call is audited with model, served-by model and token usage.
    • The engine records whether each sent email started from the template or from Claude, and measures edits against that draft. Insights reports both edit rates and suggests template or prompt reviews.

  8. Business rules are configuration. Validations, fee calculations and decision tables live in versioned rule sets (config/rules/), written in a small, safe expression language that is checked at startup. A rule set runs as a playbook step (rules.evaluate). Its result is stored on the task, later steps can read it (steps['id'].outputs…), and any step can be made conditional on it with when (false means skipped and audited; an error goes to a person). Each rule set carries test cases that npm test runs. Clients can swap a rule set via ruleSetOverrides. See RULES.md.

  9. External systems are configuration, and TRAC is one of them. Each system (config/integrations/) declares its URL, auth (secrets by environment variable name only), timeout, retry policy and operations, with request bodies and response mappings written in the rules language. Steps call them with integration.call, and the built-in TRAC actions use the same client. Only idempotent operations are retried, and they carry an idempotency key. Failures after retries become exceptions for a person. The call log records outcomes and timing, never bodies or secrets. Built-in mocks behind mock:// URLs keep the demo and tests self-contained while exercising the same HTTP contract. The engine is async, with work on each case serialized. See INTEGRATIONS.md.

  10. AI agents are steps, and their output is a proposal. An ai.agent step must be REVIEW mode. The agent runs when the step becomes ready. It sees only its configured input, can call only read-only integration operations, and must return its output schema. A person approves or edits the proposal, which is validated again, and only the approved result feeds later steps. A rule set after the agent checks the approved output. If AI is unavailable, the person enters the result by hand. See AGENTS.md.

So a process mixes four kinds of step: integration (fetch or update an external system), rules (logic and decisions), AI agent (proposal) and person (review, approval, manual work), connected by dependencies and when conditions and passing data through steps['<id>'].

Task state machine

BLOCKED ──deps done──► (step `when` false ─► SKIPPED)
                         READY ──(AUTO)──► run ──ok──► DONE
                         │                  └─fail─► READY + exception ─► routed to a person
                         ├──(REVIEW/MANUAL)─► routed ─► IN_PROGRESS ─► DONE
                         └── no eligible user ─► stays in skill queue; re-routed when
                                                 capacity frees up or users are imported
Case: OPEN ─all tasks DONE/SKIPPED─► COMPLETED      (cancel ─► CANCELLED, open tasks SKIPPED)

Routing policy

Eligible users are active, hold the task's skill at or above minSkillLevel, and are below capacity. Skill level decides who may take a task (for example, sponsor verification, 408(b)(2) disclosures and contact-change call-backs need COMPLIANCE level 2+); it does not decide who gets it. Among eligible users the router picks the lowest load ratio (open tasks ÷ capacity), then whoever was assigned work least recently (round-robin, taken from the strictly ordered audit log), then user id. Equally loaded people therefore take turns, so work is split evenly regardless of seniority. With no eligible user the task waits in the unassigned queue, and Insights reports the backlog by skill.
