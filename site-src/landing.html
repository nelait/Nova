How it works

One request, four kinds of step

Each process is a playbook of steps. Every step is one of four kinds, and each step passes its result to the steps after it.

Integration

Call your systems

Read from or write to the recordkeeper, a fund catalog or a CRM. The address, sign-in, retries and request mapping are configuration.

Install the plan on TRAC with an idempotency key, so a retry never creates a second plan.

Rules

Apply your rules

Validations, fee calculations and decision tables, written in a small, safe formula language. Every rule set has its own test cases.

Flag a contact change to a free-mail address as a possible fraud attempt.

AI agent

Let AI propose

An agent sees only the data you give it and can only look things up. What it produces is a proposal for a person to approve.

Propose where balances in removed funds should move, with a reason for each.

Person

Keep people in charge

Reviews, call-backs and approvals go to someone with the right skill and level, with guidance and a checklist.

Only Compliance level 2 or above can verify a plan sponsor.

Plan lifecycle

From onboarding to deconversion

Five processes cover a plan's time with you. Each is a versioned playbook, and any client can have its own variant.

ERISA 408(b)(2) · QDIA

Onboarding

  • Validate the application and classify the plan by size
  • Check every fund against the fund catalog
  • Verify the sponsor and the authorized signer
  • Send the fee disclosure and the welcome email
  • Install the plan on the recordkeeper
404(c)(4) notice: 30–60 days

Plan changes

  • Contact changes, with a call-back to the number on file
  • Fund lineup changes, with an AI-proposed fund mapping
  • Fee changes, with an updated disclosure
  • Every change applied on the recordkeeper
ERISA 101(i) blackout notice: 30+ days

Termination

  • Verify the board's authorization
  • Calculate prorated fees for review
  • Send the blackout notice and the confirmation
  • Terminate the plan on the recordkeeper
Controls

Built for work that gets audited

Plan operations is regulated work. These safeguards are part of the engine, so nobody has to remember to switch them on.

AI proposes, people approve

Steps that run an AI agent must be review steps. Nothing an agent produces is used until a person approves it, and AI never decides which steps run.

Facts can't go missing

Every value a template puts in an email (a fee, a date, a ticker) must still be there after anyone edits it, or the email can't be sent.

Qualified people only

Steps can require a minimum skill level. Every compliance step needs level 2 or above, and a test keeps it that way.

Retries never double-post

Writes to external systems carry an idempotency key, so a step retried after a timeout is applied once.

Failures go to a person

When an automatic step fails, the case doesn't stall. The step goes to someone with the reason, who can fix and retry, or override with a written justification.

A complete audit trail

Every routing decision, approval, edit, override and external call is recorded with who, when and why.

Secrets stay out of config

Credentials come only from environment variables. The app shows whether a secret is set, never its value, and call logs never store request bodies.

Agents see only what they need

Each AI agent receives only the case fields its configuration lists, so details like EINs and contact emails are never sent to it.

The product

What your team works in

Each person sees the work routed to them, with the guidance, checklist and prepared work for each task.

Configure, don't code

Your operating procedures, as reviewable files

  1. Describe each process as a playbook: steps, skills, dependencies and conditions.
  2. Write rules as formulas, with test cases that run on every change.
  3. Connect a system by describing its operations, with no adapter code.
  4. Give a client its own variant of any process, template or rule set.
